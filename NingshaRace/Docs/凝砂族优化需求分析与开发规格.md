# 凝砂族优化需求分析与开发规格

> 面向 RimWorld 1.6 的实现说明。本文把两张反馈截图转换为可直接交给 AI 或开发者执行的任务规格，并以当前工程代码与原版源码行为为依据。

## 2. 一页结论

本轮 8 项优化均已完成代码接入。太阳能板已先增加沙漠巨坑定向放置限制；若限制之外仍出现红字，仍需取得完整堆栈定位真实来源。

最重要的三个结论如下：

1. **地底连锁塌方不是随机生成瑕疵，而是屋顶类型选错。** 沙漠巨坑全图使用可坍塌的厚岩顶；玩家建造的墙成为临时屋顶支撑，拆墙后原版会重新检查大范围无支撑屋顶，从而触发连锁坍塌。
2. **祭坛任务“删除后仍占用”符合当前代码逻辑。** 原版任务页的“删除/隐藏”只设置 `dismissed`，不会结束任务；当前世界组件又只按 `QuestState` 判断占用，所以任务槽不会释放。
3. **蜕皮按钮其实已经存在，但只在营养满时出现。** 玩家在积攒期间看不到按钮和独立进度条，因此机制像是“没有入口”。应改为进度条常显、按钮常显但条件不足时禁用。

## 4. 默认决策

| 决策点 | 默认值 | 理由 |
| --- | --- | --- |
| 沙傀存在时间 | `60000` tick，即 1 游戏日 | 时间足够完成一次常规战斗，且便于玩家理解为 24 小时 |
| 沙傀时间显示 | 进度条 + 剩余小时/时间文本 | 同时满足快速扫视与精确判断 |
| 侵蚀体活铁掉落 | 固定 `8` 个 `Plasteel` | “少量”定位明确，且可纯 XML 实现 |
| 祭坛拒绝退款 | 不退还任何营养 | 与截图明确要求一致；任务发布时已经消耗 100 营养 |
| 已接受任务的“删除” | 不释放祭坛任务槽 | 已接受任务仍在进行，隐藏 UI 不等于放弃任务 |
| 未接受任务的“删除” | 视作拒绝并释放任务槽 | 防止隐藏的任务提案永久占用祭坛 |
| 地底太阳能板 | 在沙漠巨坑内禁止放置 | 全图有厚岩顶，太阳能板本就没有合理发电条件 |
| 洞穴物件掉落触发方式 | 仅玩家“拆除”时触发 | 避免战斗破坏、开发者删除也刷出资源 |

## 5. OPT-01：沙傀有限寿命与存在时间条

### 5.1 当前证据

- `SandGolem/Defs/SandGolemDefExtension.cs` 目前只有动画时长、维护间隔和技能回退等级，没有寿命配置。
- `SandGolem/Rendering/SandGolemRenderState.cs` 保存召唤者、沙傀、阶段和阶段开始时间，没有到期时间。
- `SandGolem/Tracking/GameComponent_SandGolemTracker.cs` 管理聚沙、稳定、消散三个阶段，但稳定阶段不会因时间自动结束。
- `SandGolem/Patches/SandGolemPatches.cs` 已经向沙傀的 `Pawn.GetGizmos` 注入“收回沙傀”，可在同一入口增加寿命 Gizmo。

因此，“只画一个条”无法形成真实机制。必须先建立可持久化的寿命，再让 UI 读取同一数据源。

### 5.2 目标行为

- 沙傀完成召唤、进入稳定阶段时，寿命为满值。
- 默认存在 60000 tick；进度条随剩余时间连续缩短。
- UI 显示可读的剩余时长，例如“剩余 13.4 小时”。
- 时间耗尽后自动进入现有消散动画，不瞬间删除。
- 手动收回、重新召唤替换、召唤者失效和自然到期都走同一套消散流程。

### 5.3 实现规格

1. 在 `SandGolemDefExtension` 增加 `lifetimeTicks = 60000`。
2. 在 `SandGolemRenderState` 增加并保存绝对时间 `expireTick`，避免暂停、存档和读档导致计时漂移。
3. 新沙傀注册时设置 `expireTick = 当前 tick + animationTicks + lifetimeTicks`；汇聚阶段显示满条，完成汇聚后从完整寿命开始递减。
4. `GameComponent_SandGolemTracker` 在维护更新中检查稳定沙傀是否到期；到期时调用现有 `BeginDissolve`。
5. 新建 `SandGolem/UI/Gizmo_SandGolemLifetime.cs`，只负责展示，不自行修改生命周期。
6. 在现有 `Pawn.GetGizmos` 补丁中，仅为有效沙傀加入寿命条，并保留“收回沙傀”命令。

### 5.4 UI 规范

- 建议尺寸：`180 × 75`，与现有侵蚀值面板保持同一视觉语言。
- 标题：“沙傀存在时间”。
- 进度：`Clamp01((expireTick - 当前 tick) / lifetimeTicks)`。
- 文本：剩余时间；鼠标提示补充总时长和到期后自动消散说明。
- 绘制后必须恢复 `Text.Font`、`Text.Anchor`、`Text.WordWrap` 和 `GUI.color`。

### 5.5 验收标准

- [ ] 新召唤沙傀的条为满值，随后单调缩短。
- [ ] 保存、读档后剩余时间不重置。
- [ ] 时间归零只触发一次消散，不重复销毁或重复报错。
- [ ] 手动收回与二次召唤仍能正常工作。
- [ ] 沙傀死亡、离图或引用失效后不留下空 Gizmo 或跟踪状态。

## 6. OPT-02：沙漠巨坑稳定岩顶

### 6.1 根因

当前存在两处全图铺设 `RoofRockThick` 的逻辑：

- `DesertPit/Generation/Progress/DesertPitPocketMapGeneration.cs` 在创建地图时填充厚岩顶。
- `DesertPit/Generation/Steps/GenStep_DesertPitTerrain.cs` 又把每个格子的屋顶设置为 `RoofDefOf.RoofRockThick`。

原版 `Building.DeSpawn` 会在拆除 `holdsRoof` 建筑时通知 `RoofCollapseCellsFinder`。可坍塌屋顶一旦失去支撑就会被成片检查；厚岩顶坍塌后不会像薄屋顶一样简单消失，因此会形成危险的连续坍塌。

### 6.2 目标行为

- 沙漠巨坑继续被视为天然厚岩顶区域，保留地下温度、遮蔽与头顶山体语义。
- 玩家新建、拆除墙体或柱子时，不触发该地图的屋顶坍塌。
- 地表地图及其他模组地图仍使用原版坍塌规则。

### 6.3 实现规格

1. 新建专用 `RoofDef`：`NingshaRace_DesertPitStableRockRoof`。
2. 该屋顶应是天然厚岩顶，但设置 `canCollapse=false`。
3. 在 `NingshaRace_DesertPitMap.xml` 的地图生成器中设置 `<roofDef>` 为该 Def。
4. `GenStep_DesertPitTerrain` 不再写死 `RoofDefOf.RoofRockThick`，改为同一个专用 Def 或读取当前地图生成器的 `roofDef`。
5. 两处赋值必须共用一个来源，防止未来再次出现初始化屋顶与地形步骤不一致。

### 6.4 明确禁止

- 不得全局跳过 `Building.DeSpawn` 的屋顶检查。
- 不得全局修改 `RoofRockThick.canCollapse`。
- 不得用吞异常或事后删除坍塌岩块来掩盖问题。

### 6.5 验收标准

- [ ] 在巨坑内建墙后拆墙，不出现坍塌或连锁坍塌。
- [ ] 拆除连续墙、单独支柱以及洞穴边缘支撑都不会坍塌。
- [ ] 巨坑仍显示头顶山体，相关地下判定不变。
- [ ] 普通地表地图的屋顶坍塌仍按原版运行。

## 7. OPT-03：侵蚀体死亡掉落活铁

### 7.1 当前证据

- `Defs/Erosion/Mutants/NingshaRace_ErosionBodyMutant.xml` 没有配置死亡遗留物。
- `CompNingshaErosion.Notify_Killed` 目前只取消转化过程，不生成掉落。
- 原版 `MutantDef` 原生提供 `List<ThingDefCountClass> killedLeavings`；原版死亡遗留物流程会读取该列表。

### 7.2 推荐方案

直接在侵蚀体的 `MutantDef` 中配置固定 `8` 个 `Plasteel`。这是数据层能力，不需要为一次简单掉落增加 C# 死亡补丁，也不会让正常凝砂族死亡时误掉活铁。

只有未来明确要求“随机范围、受侵蚀值影响或受伤害类型影响”时，才改为专用 `ThingComp`。

### 7.3 验收标准

- [ ] 侵蚀体死亡后生成 8 个活铁。
- [ ] 普通凝砂族死亡不生成这份掉落。
- [ ] 不因尸体生成、屠宰或死亡清理产生第二份活铁。

## 8. OPT-04：智慧之蛇祭坛优先填充

### 8.1 当前证据

`Altar/Components/CompAltarOffering.cs` 已有右键“优先填充智慧之蛇祭坛”的单殖民者入口，`WorkGiver_FillWisdomSerpentAltar.cs` 也支持自动工作。因此截图反馈更像是入口覆盖不足或判定分叉，而不是功能完全不存在。

当前风险包括：

- 单选殖民者与多选殖民者走不同的浮动菜单入口，多选时可能没有命令。
- 手动入口和自动 `WorkGiver` 各自查找生肉，规则未来容易漂移。
- 祭坛不可达、被预定、已满、未占用或没有合法生肉时，玩家缺少明确原因。

### 8.2 目标行为

- 单选或多选己方殖民者后右键祭坛，都能看到“优先填充智慧之蛇祭坛”。
- 条件满足时立即下达强制工作。
- 条件不满足时保留灰色选项，并准确说明唯一的主要阻塞原因。
- 自动搬运和手动优先使用完全相同的合法生肉、数量、距离和预定规则。

### 8.3 实现规格

1. 新建 `Altar/Jobs/AltarOfferingJobUtility.cs`，集中负责：
   - 判定祭坛是否可供奉；
   - 筛选合法生肉；
   - 查找最近可达且可预定的来源；
   - 计算本次需要携带的数量；
   - 返回失败原因。
2. `WorkGiver_FillWisdomSerpentAltar` 与右键命令都调用该工具，不再各写一套筛选。
3. 保留 `CompFloatMenuOptions` 的单人入口，并补上 1.6 对应的多选殖民者入口。
4. 多选时按每名合格殖民者生成带姓名的选项；点击后只给该殖民者派发工作，避免一次点击抢占同一堆生肉。
5. Job 开始前同时预定祭坛和生肉；失败直接给出原版式提示，不静默吞掉。

### 8.4 验收矩阵

| 场景 | 期望结果 |
| --- | --- |
| 单选殖民者、附近有生肉 | 可强制填充 |
| 多选殖民者、附近有生肉 | 每名合格殖民者有清晰选项 |
| 祭坛未占用 | 灰色选项说明需先占用 |
| 祭坛已满 | 灰色选项说明供奉已满 |
| 没有生肉 | 灰色选项说明缺少合法生肉 |
| 生肉被禁用、不可达或已预定 | 显示对应阻塞原因 |
| 自动搬运 | 与手动入口使用同一筛选规则 |

## 9. OPT-05：拒绝指引任务并正确释放祭坛

### 9.1 根因

任务发布后，`AltarMissionWorldComponent` 保存 `activeQuestId`。当前 `HasActiveMission` 只会在任务不存在，或状态不再是 `NotYetAccepted`/`Ongoing` 时释放它。

原版任务页对尚未成为历史记录的任务执行“删除”时，只设置 `quest.dismissed`，不会改变 `QuestState`。因此：

```text
任务被隐藏 → QuestState 仍是 NotYetAccepted → activeQuestId 仍有效 → 祭坛继续显示“正在指引”
```

### 9.2 状态规则

| 当前状态 | 玩家动作 | 营养 | 任务处理 | 祭坛槽位 |
| --- | --- | --- | --- | --- |
| `NotYetAccepted` | 接受 | 已消耗，不退款 | 转为进行中 | 继续占用 |
| `NotYetAccepted` | 专用“拒绝指引” | 已消耗，不退款 | `InvalidPreAcceptance` | 立即释放 |
| `NotYetAccepted` | 原版删除/隐藏 | 已消耗，不退款 | 视作拒绝并结束 | 最迟 60 tick 内释放 |
| `Ongoing` | 原版删除/隐藏 | 不涉及退款 | 仅隐藏 UI，任务继续 | 继续占用 |
| 已结束或任务不存在 | 任意 | 不涉及退款 | 清理引用 | 释放 |

### 9.3 实现规格

1. 在 `AltarMissionWorldComponent` 增加职责明确的接口，例如：
   - `IsRegisteredMission(Quest quest)`：确认任务是否是当前祭坛指引；
   - `TryRejectOffer(Quest quest)`：只拒绝 `NotYetAccepted` 的当前祭坛任务；
   - `ReconcileActiveMission()`：统一清理不存在、已结束和被隐藏的未接受任务。
2. 拒绝时调用原版 `quest.End(QuestEndOutcome.InvalidPreAcceptance, sendLetter: false, playSound: false)`，随后释放 `activeQuestId`。
3. 在世界组件原有低频检查中，把“`dismissed && NotYetAccepted` 的祭坛任务”当作隐式拒绝，避免玩家使用原版删除后留下永久占用。
4. 对任务界面做窄范围 Harmony 补丁：仅在当前选中任务是未接受的祭坛指引时，在接受按钮旁绘制“拒绝指引”。
5. 点击拒绝先弹确认框，明确写出“本次供奉已消耗的 100 营养不会返还”。
6. 已接受任务不显示专用拒绝按钮。本轮不设计中途放弃任务。

建议文件：`AltarMissions/UI/Patch_MainTabWindow_Quests_RejectAltarMission.cs`。任务 UI 属于原版私有布局，补丁必须只承担按钮注入，不把任务状态规则塞进 UI 类。

### 9.4 验收标准

- [ ] 尚未接受的祭坛任务显示“接受”和“拒绝指引”。
- [ ] 拒绝有确认提示，确认后任务结束、祭坛立即可再次积累与发布。
- [ ] 拒绝后不返还 100 营养。
- [ ] 对未接受任务使用原版删除，最迟 60 tick 后祭坛槽释放。
- [ ] 已接受任务即使被原版隐藏也继续占用，直至真实结束。
- [ ] 普通原版任务和其他模组任务不出现该按钮。

## 10. OPT-06：蜕皮营养可视化与主动入口

### 10.1 当前证据

- `Molting/Components/CompNingshaMolting.cs` 已保存营养、蜕皮次数，并已有主动“蜕皮”命令。
- 主动命令目前只在营养达到 100 且蜕皮次数未满 20 时返回，所以绝大多数积攒时间里玩家看不到它。
- 营养值目前主要出现在检查字符串中，没有类似侵蚀值的醒目进度条。
- `Erosion/UI/Gizmo_NingshaErosion.cs` 已提供项目内可复用的样式与 GUI 状态保护范例。

### 10.2 目标行为

- 玩家选中己方凝砂族时始终看到“蜕皮营养”进度条。
- 主动蜕皮图标始终可见；条件不足时禁用，并说明还差多少营养或已经达到 20 层上限。
- 玩家能直接理解两条消费规则：主动蜕皮需要 100，致命伤保命需要 60。

### 10.3 实现规格

1. 为组件增加只读比例与剩余需求属性，所有 UI 只读取组件状态。
2. 新建 `Molting/UI/Gizmo_NingshaMoltingNutrition.cs`。
3. Gizmo 建议尺寸 `180 × 75`，排序紧邻侵蚀值；显示 `当前值 / 100`。
4. 状态文字建议使用“主动蜕皮需 100 · 保命需 60”，避免玩家误以为 60 已能主动蜕皮。
5. 复用现有 `UI/Commands/Molting` 图标；删除“营养不满就不生成命令”的隐藏逻辑，改成禁用逻辑。
6. 只为己方、已生成、具备凝砂蜕皮组件的 Pawn 展示，避免出现在敌人或世界 Pawn 上。

### 10.4 验收标准

- [ ] 营养从 0 到 100 的变化实时反映在进度条。
- [ ] 0 营养时仍看得到主动蜕皮按钮，按钮为禁用状态并说明差 100。
- [ ] 99 营养时说明差 1；100 时可用。
- [ ] 达到 20 层后按钮禁用并说明已达上限。
- [ ] 与侵蚀值 Gizmo 同时显示时不重叠、不污染后续 GUI 样式。

## 11. OPT-07：沙漠巨坑太阳能板报错

### 11.1 已知与未知

已确认：沙漠巨坑当前全图覆盖厚岩顶；用于照明的裂隙是带发光组件的建筑，并不是真正的露天格。原版太阳能发电组件本身主要读取天光与屋顶系数，仅凭现有工程代码无法证明“大量红字”的确切调用栈。

因此，本项不能凭猜测写全局异常补丁。实施前必须保留第一次红字及完整堆栈，至少包含：

- 异常类型和第一条异常文本；
- 第一个非原版方法；
- 是否安装了改造太阳能板或电网的其他模组；
- 报错发生在蓝图放置、施工完成、逐 tick 发电还是地图卸载阶段。

### 11.2 默认处理

无论堆栈来自原版还是联动模组，当前地图设计下太阳能板位于厚岩顶下不会正常获取日照。默认增加一个定向 `PlaceWorker`：

- 只在 `map.generatorDef == NingshaRace_DesertPitMap` 时拒绝太阳能板蓝图；
- 提示“沙漠巨坑的厚岩顶无法接收日照”；
- 不影响地表地图，不修改太阳能板发电公式；
- 若堆栈证明是其他独立问题，再按首个责任方法另开修复项。

### 11.3 验收标准

- [ ] 巨坑内无法放置太阳能板，并有明确原因。
- [ ] 地表地图仍可正常放置太阳能板。
- [ ] 不通过吞异常、屏蔽日志或全局禁用太阳能组件实现。
- [ ] 若仍有红字，文档化完整堆栈后再修复真实来源。

## 12. OPT-08：可拆除洞穴物件与概率回收

### 12.1 根因

`ThingDef_NingshaRace_DesertPitDecorations.xml` 的装饰基类当前组合了以下设置：

- `selectable=false`
- `destroyable=false`
- `useHitPoints=false`
- `deconstructible=false`
- `isTargetable=false`
- `isEdifice=true`

这些物件既会占据建筑格，又没有玩家交互入口，所以即使开发者模式在其上放置墙体，也不会自动消失。

此外，`GenStep_DesertPitTerrain.cs` 还会生成原版 `CollapsedRocks` 和 `ChunkSandstone`。前者是不可拆除的可开采建筑，后者是可搬运物品；两者都不符合“统一拆除并按给定概率结算”的需求。

### 12.2 目标行为

- 洞穴里的大小石头和装饰都能被选中并下达拆除命令。
- 拆除完成后只抽取一次结果，四种结果互斥。
- 资源概率与数量严格如下：

| 概率 | 掉落 |
| ---: | --- |
| 50% | 40 个砂岩砖 `BlocksSandstone` |
| 25% | 30 个原木 `WoodLog` |
| 15% | 25 个钢铁 `Steel` |
| 10% | 10 个零部件 `ComponentIndustrial` |

### 12.3 实现规格

1. 调整凝砂洞穴装饰抽象基类，使其可选中、可受伤、可成为目标并可拆除。
2. 为物件设置合理的 `MaxHitPoints` 与拆除工作量；保留不需要占用/宣称的地下自然物定位。
3. 为巨坑生成使用的大小石块建立凝砂专用 Def，并让生成步骤不再直接生成原版 `CollapsedRocks`/`ChunkSandstone`。
4. 新建独立回收模块：
   - `DesertPit/Salvage/Components/CompDesertPitSalvage.cs`
   - `DesertPit/Salvage/Components/CompProperties_DesertPitSalvage.cs`
   - 可选的权重数据类按职责单独成文件。
5. 在 `ThingComp.PostDestroy(DestroyMode, Map)` 中，仅当 `DestroyMode.Deconstruct` 时抽取一项并在原位置附近生成掉落。原版 `GetAdditionalLeavings` 只参与击毁遗留物结算，不能用于拆除奖励。
6. 普通建造成本返还比例设为 0，且不要用 `costList` 表达这份随机奖励，避免固定返还与随机掉落叠加。
7. 权重必须在 Def 解析时校验为正数且合计大于 0；配置错误直接记录清晰错误，不静默回退到另一套奖励。

### 12.4 边界规则

- 战斗打爆、矿塌压毁、开发者删除和 `Vanish` 不掉落奖励。
- 每个物件只抽取一次，不把四个百分比当成四次独立判定。
- 不修改原版 `CollapsedRocks`，避免改变所有地图与其他模组。
- 本项目默认不兼容旧地图；旧地图上已生成的原版岩块不做批量迁移。

### 12.5 验收标准

- [ ] 所有凝砂洞穴装饰与专用大小石块均可选择、可拆除。
- [ ] 拆除后只出现四种奖励之一。
- [ ] 四项配置权重分别为 50/25/15/10，数量准确。
- [ ] 直接摧毁物件不产出回收奖励。
- [ ] 装饰清除后原位置可以正常建造墙和其他建筑。

## 13. 推荐实施顺序

| 阶段 | 工作项 | 原因 |
| --- | --- | --- |
| A | OPT-02 稳定岩顶 | 高风险地图问题，且会影响建筑/拆除验收 |

| C | OPT-04 祭坛优先填充 | 与任务入口同属祭坛闭环，可一起回归 |

每一阶段都应独立编译，避免把地图生成、任务 UI 和 Pawn 生命周期错误混在一次构建中。

## 15. 编码约束

- 每个类、每个函数都写中文职责注释；复杂状态转换补必要的中文行内说明。
- 不写旧存档迁移，不增加大范围兜底；配置或状态错误应输出可定位的错误。

## 17. 人工运行时测试清单

开发者编译完成后，建议人工按下列顺序测试：
