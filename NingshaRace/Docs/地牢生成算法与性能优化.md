# 地牢生成算法与性能优化

## 范围与交付状态

适用于 `NingshaRace_GiantTombMap` 的 200×200 巨型墓葬，以及复用该求解器的 120×120 祭坛小型遗迹。不更改模板文件、敌人奖励表、矿物种类、入口出口语义，也不减少巨型墓葬的 19 种必选模板和 24–32 个额外实例。

代码与 Release DLL 已更新；编译通过，保留既有 MSB3270（项目 MSIL 与 HarmonyMod AMD64）警告。未启动 RimWorld，未执行算法测试程序或性能基准，未同步至游戏 Mods 目录。不能据此宣称已实测提速多少。

## 热点与实现入口

源码根目录为 `1.6/Source/NingshaRaceLib/GiantTomb/`。

| 原有开销或问题 | 当前处理 | 源码入口 |
| --- | --- | --- |
| 每次搜索尝试重复计算模板变换 | 主线程准备一次只读几何目录，正常和紧凑尝试共享 | `Layout/Search/GiantTombSearchCatalog.cs` |
| 每层递归重新枚举出口坐标与碰撞，选中后又计算一次 | 出口几何缓存、增量碰撞失效、按房间撤销，选中后直接复用 | `Layout/Search/GiantTombFrontierDomain.cs`、`GiantTombFrontierSet.cs` |

## 候选缓存的不变量

1. 出口的父房间和创建时祖先前缀在出口存活期间不会被替换，因此只有这部分碰撞可以永久排除。
2. 延迟到深层才首次准备的出口仍只按创建前缀永久排除；后加入的房间必须通过可撤销失效日志处理。
3. 每个失效候选只登记第一个阻挡它的房间。后进先出的回溯保证撤销该阻挡房间时，更晚的房间已全部撤销。
4. 回溯还会缩短出口已检查前缀，确保同深度的兄弟房间被重新检查，不误用上一分支的缓存。
5. 模板实例耗尽不永久删除几何候选；通过实例栈数量判断当前可用性，实例恢复后候选自动重新参与。
6. 最少候选出口选择、全部接口闭合、父子可贴边、非父子保留一格岩层和候选评分偏好仍然保留。

这是以出口候选内存换取重复几何计算减少的策略，不是所有尺寸和种子都必然更快。撤销日志和位图只属于本次求解器，搜索结束即可释放，不跨地图缓存。

## 搜索预算

| 字段 | 巨型墓葬 | 祭坛小型遗迹 | 语义 |
| --- | ---: | ---: | --- |
| `maxRestarts` | 32 | 32 | 两阶段尝试总上限；正常最多 8 次，紧凑最多 24 次 |
| `maxCandidateEvaluations` | 500000 | 240000 | 正常阶段全部尝试的候选摆放总预算 |
| `maxCompactCandidateEvaluations` | 2400000 | 2400000 | 紧凑阶段全部尝试的独立候选摆放总预算 |

因此当前巨型墓葬候选预算上限为 2900000，小型遗迹为 2640000。每阶段均分预算，余数依次分配给前几个尝试；候选预算小于尝试数时同步减少尝试数，保证每次至少一个候选且总额不超限。`maxRestarts <= 8` 时一般没有紧凑尝试余量。

预算限制的是尝试进入的摆放分支，不是毫秒数，也不包含该分支内部所有矩形谓词检查。每个分支仍保留最多 256 个评分候选，因此这不是穷举证明器；失败提示只表示在预算内未得到完整结果。

紧凑阶段继续使用全部必选模板，把额外实例数取配置下限并优先选择较小的重复模板；不追加无限轮次、不输出半张地牢、不静默退回旧沙坑。

## 线程与生命周期

- 主线程负责加载模板、读取许可变换、构造几何目录、抽取模块池与局部随机种子。
- `GiantTombParallelLayoutSearch.Execute` 内部完成并行计算、线程安全汇总和结果选择；只有完整结果可以交给主线程写图。
- 各工作线程独占实例栈、空间索引、候选缓存和撤销日志，只读共享几何；不调用全局 Rand 或地图状态写入接口。
- 同批次选择编号最小的成功尝试。更高编号可以提前结束，不能让先完成的高编号方案抢占结果。
- 生成枚举器退出时通过 `Dispose` 请求停止并等待线程收束，不让失败地图清理和仍在计算的搜索脱节。

## 同步处理的正确性问题

- 变换预计算遵守 `ClCompiledMapTemplate.AllowRotation/AllowMirror`，避免求解器选择框架实际拒绝的变换。
- 入口先确认存在许可的朝北变换，再检查地图安全边界。
- 布局 Def 的空模块列表检查不会继续对空引用调用 `Contains`；边缘宽度必须留下有效内部范围。
- 原版 `TerrainGrid.SetTerrain` 本身会清除涂色，因此背景恢复不再紧接着无条件调用 `SetTerrainColor`。地形变化仍使用原版接口维护水格、发光地形和事件，不直接改写这些运行期内部表。

API 核对来源为本地原版 `Verse/CellRect.cs`、`Verse/TerrainGrid.cs`，以及 `E:/RimModDev/ChezhouLib/Source/ChezhouLib/CustomMission/MapTemplates` 中的变换、编译模板和实例化源码。

## 结果与后续人工验收

新地图的具体形状、房间选点和后续随机结果可能与优化前不同；不承诺跨版本同种子逐格一致。已有地图不重建、不迁移。

本次只完成源码审查、XML/编码静态检查和编译。以后手工进入游戏时关注：

- 巨型墓葬和小型遗迹都可生成完整房间、连通通路和可用出口，且没有重叠或悬空接口。
- 反复回溯后仍不发生重叠；正常与紧凑阶段都保留必选房间。预算极低或配置无法容纳时明确失败，不持续开启下一轮。
- 奖励拆堆、蚁穴占地和储藏格不重复占用，连接口保护区保持为空。
- 同一构建、模板和 Def、世界状态及种子下结果可复现；并发调度允许改变诊断计数和耗时，不应改变被选中的布局。
- 查看 `巨型墓葬并行布局完成` 的阶段、候选数、碰撞检查数、耗时，以及整张地图的分步骤用时；冷模板加载与缓存命中分开比较。阶段日志包含分帧等待，不能直接当作纯 CPU 时间。

如仍然缓慢，先依据实际日志判断是拼接、模板实例化、敌人生成还是 `FinalizeInit`，不要在没有测量的情况下继续增加并发数或缩减地图内容。
